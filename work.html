01 Safety

The anti-nuke engine

A compromised admin can strip a server in minutes. Kernel keeps a copy of what the server looked like before that happens, a way to lock it down mid-incident, and a repair path for after.

The problem

A rogue admin or a stolen token does not need to be clever. Deleting channels, stripping roles and rewriting permissions is enough. Discord's audit log records who did what, but it does not hold a copy of how the server used to look — so rebuilding by hand becomes guesswork under pressure.

What we built

  • Snapshots. Channels, roles and permissions are copied on demand so a restore has something real to work from.
  • Panic lock. /antinuke can lock the server down mid-incident instead of waiting for the damage to finish.
  • Damage repair. A snapshot can be compared against the live server and put back where it is safe to do so.
  • Power audit. /security lists who actually holds dangerous permissions and tells you when that changes overnight.
  • Webhook and bot landing guards. /nukehooks, /antiwebhook and /botlanding cover the quieter ways in.

How it is checked

Every module passes the release gate: it compiles, its slash options validate, and the API suite covers the endpoints around it. The risky parts are kept small and readable on purpose — restore and lock logic is the kind of code that has to be auditable at 2 a.m., not clever.

What it does not do

A restore is only as good as the last snapshot. If none was taken, there is nothing to put back — the guard cannot invent a past it never recorded. Keeping snapshots on is part of using it.

02 Evidence

The case ledger

A moderation record that stops verifying the moment somebody edits it. Every case carries the hash of the case before it, so a rewritten history fails its own check.

The problem

Moderation history is easy to corrupt quietly — a log channel gets trimmed, a record gets edited, and the screenshot someone saved last month becomes the only copy. A ban list without a chain of custody is a story, not evidence.

What we built

  • Chained cases. Each moderation case stores the hash of the previous one, so the record forms a chain.
  • Verifiable reads. /cases reads the record and checks the chain, instead of trusting whatever is on disk.
  • A second record. /audit searches Discord's own audit log for who changed what, next to what Kernel recorded.
  • Newest first. /banlist and the case views read the same record, so the numbers cannot disagree with each other.

How it is checked

The chain is its own test: edit any case in the middle and the verification fails at that case. The command that reads it ships through the same release gate as everything else, and its options are validated before the bot connects.

What it does not do

The chain proves the record you hold was not edited in place. It cannot prove what happened on Discord that was never recorded. Evidence of absence is not what a hash chain is for.

03 Control

The owner console

Owner-only controls without a password to leak. The console is a static page that talks to the bot, and the bot only answers the Discord account that owns it.

The problem

Running a bot needs owner tools: broadcasts, backups, scheduled jobs, a way back from a bad release. Building an admin panel with its own accounts means storing credentials, and storing credentials is how small projects grow their first breach.

What we built

  • A Discord-ID gate. Owner routes live under /api/owner/* and answer only the owner's Discord ID; everyone else gets a 404.
  • Owner console pages. Broadcasts, backups, drift checks, the watchlist, scheduled jobs and release rollbacks.
  • An error inbox. Errors the bot records are readable without digging through host logs by hand.
  • No secret storage. The console keeps no passwords, IP addresses, location data or login history.

How it is checked

The API suite covers the owner gate and the settings routes around it, and the browser sweep loads the console pages alongside the public site — clean console, no broken requests — before a release is packaged.

What it does not do

If the bot is asleep, the console cannot act. It is a static site calling your bot, not a second backend. There is no Kernel cloud service holding a copy of your data.
